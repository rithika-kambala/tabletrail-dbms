# TableTrail viva preparation

| Question                                            | Short answer                                                       | Explanation and implementation                                                                                                                                         |
| --------------------------------------------------- | ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Why is this a DBMS project?                         | Business rules and reports depend on relational operations.        | MySQL constraints, joins, views, routines, triggers and transactions drive checkout and analytics, not just record forms. See database/ and backend/src/analytics.js.  |
| Why normalize the schema?                           | To reduce anomalies and duplication.                               | A customer email appears once in customers; orders reference customer_id. Changing an email cannot leave inconsistent order copies. See schema.sql.                    |
| How do you demonstrate 1NF?                         | Atomic fields and separate item rows.                              | order_items has one row per dish in an order rather than a comma-separated dish list.                                                                                  |
| How do you demonstrate 2NF?                         | Composite-key attributes depend on the whole key.                  | inventory.quantity depends on branch_id AND ingredient_id, not either alone.                                                                                           |
| How do you demonstrate 3NF?                         | Descriptive fields stay in their own entities.                     | menu_items stores category_id; menu_categories stores category name. No transitive category-name dependency remains in menu_items.                                     |
| What is a candidate key?                            | A minimal attribute set that uniquely identifies a row.            | employees.id and employees.email are candidate keys; id is selected as the primary key. Email has UNIQUE and NOT NULL.                                                 |
| Where is a composite key useful?                    | Junction tables.                                                   | recipes(menu_item_id,ingredient_id) prevents the same ingredient appearing twice for a dish. Quantity depends on both.                                                 |
| Where is a composite foreign key?                   | The inventory audit log.                                           | inventory_log(branch_id,ingredient_id) references the complete inventory primary key.                                                                                  |
| Give a one-to-one relationship.                     | Order to payment.                                                  | payments.order_id is UNIQUE; an order has at most one payment. The completion workflow requires payment before completed status.                                       |
| Give a many-to-many relationship.                   | Dishes and ingredients.                                            | A dish uses many ingredients and an ingredient occurs in many dishes; recipes resolves this relationship.                                                              |
| Why are payment and feedback optional?              | Orders begin pending and customers may not leave feedback.         | Both are zero-or-one per order. The API and triggers require completed status for feedback and payment for completion.                                                 |
| What is referential integrity?                      | References must point to existing parent rows.                     | An order with a nonexistent customer fails the FK. Records with transaction history are retained rather than deleted.                                                  |
| What does CHECK enforce?                            | Domain rules.                                                      | Inventory cannot be negative, recipe quantities must be positive, ratings are 1–5. CHECK requires MySQL 8.0.16+ for enforcement.                                       |
| What does the order_total function do?              | Returns the discounted payable amount.                             | It sums quantity × historical price, applies the saved promotion percentage, and rounds to two decimals. See functions.sql.                                            |
| Why preserve order prices?                          | Old transactions must not follow new menu prices.                  | order_items.unit_price is the price agreed for that order. It is a historical fact, not current menu data.                                                             |
| Procedure versus function?                          | A function returns a value; a procedure performs a workflow.       | order_total returns DECIMAL. complete_order deducts ingredients, inserts payment and completes the order.                                                              |
| Why a cursor here?                                  | To process each grouped ingredient requirement with a stock check. | The cursor aggregates quantity across dishes, orders ingredients consistently, and performs a conditional UPDATE for each. See procedures.sql.                         |
| How is double payment prevented?                    | Order lock, status check and UNIQUE payment order_id.              | A second completion waits for the row lock and then sees completed status. Even an erroneous duplicate INSERT would violate UNIQUE.                                    |
| What if stock runs out halfway?                     | The entire transaction rolls back.                                 | Earlier ingredient deductions and their audit rows are undone, no payment remains, and the order stays pending. See integration.test.js.                               |
| Explain ACID using checkout.                        | Atomicity, consistency, isolation, durability.                     | All checkout writes commit or roll back together; constraints maintain valid data; InnoDB locks coordinate requests; committed writes use MySQL durability mechanisms. |
| Can two orders oversell the last serving?           | The conditional stock UPDATE prevents it.                          | Updating only when quantity >= needed takes a row lock and checks the current stock. The concurrent-checkout integration test verifies one succeeds and one fails.     |
| What does the inventory trigger do?                 | Audits a changed quantity automatically.                           | inventory_audit writes old/new balances after UPDATE, inside the caller's transaction. It does not deduct stock a second time.                                         |
| Why not deduct stock in both a trigger and the API? | It would risk double deduction.                                    | One stored procedure owns consumption. The trigger records history only.                                                                                               |
| What is a view?                                     | A reusable named SELECT.                                           | low_stock and branch_performance centralize report logic. They are calculated from base tables, not separately maintained totals.                                      |
| INNER JOIN versus LEFT JOIN?                        | INNER needs matches; LEFT retains all left rows.                   | Order details use matched tables. branch_performance retains branches with zero completed orders. See queries.sql.                                                     |
| Where is RIGHT JOIN useful?                         | Retaining every supplier when quotes are optional.                 | The supplier example keeps right-hand suppliers with no supplier_ingredients row. Reversing the table order with LEFT JOIN is equivalent.                              |
| WHERE versus HAVING?                                | WHERE filters rows; HAVING filters groups.                         | The repeat-visit query first selects completed orders, then HAVING COUNT(*) > 1 retains repeat customers.                                                              |
| What is a correlated subquery?                      | A subquery referring to the outer row.                             | The cheapest quote example compares each supplier quote to MIN(unit_cost) for that outer ingredient.                                                                   |
| Why an index on branch/status/date?                 | To support branch order-history lookup.                            | Leading branch and status conditions match the composite index. EXPLAIN demonstrates the plan; indexes add storage/write cost.                                         |
| How is low stock defined?                           | Quantity is strictly below its threshold.                          | The view joins stock, branch and ingredient tables. Different branches can set different thresholds.                                                                   |
| Gross sales versus net revenue?                     | Gross is before discounts; net is paid after discounts.            | Item/category reports sum item prices; branch revenue sums payments. The UI labels the distinction.                                                                    |
| How does authorization work?                        | Current employee role and branch are checked server-side.          | Hiding UI buttons is not the security boundary. Middleware verifies the signed session and active user, then routes enforce access.                                    |
| How is SQL injection prevented?                     | Parameterized values and fixed identifiers.                        | mysql2 execute uses placeholders. The management table names come from a fixed catalogue allowlist, never request strings.                                             |
| Can a feedback link authenticate as staff?          | No; it has a different token audience.                             | Session verification requires audience=session. Receipt verification requires audience=feedback and exposes only one completed order.                                  |
| Why no real payment gateway?                        | It is outside the database-focused scope.                          | cash/card/upi are recorded methods. No card numbers are stored and no money is charged.                                                                                |
| What are the main limitations?                      | No refunds, reservation of stock, or recipe version history.       | Pending orders use stock and recipes at completion. Future work adds explicit reversal and revision records, not silent edits to completed orders.                     |
